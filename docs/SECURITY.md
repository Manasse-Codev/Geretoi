# Audit de sécurité DayFlow

Audit réalisé sur la branche `audit-securite`, dépôt local, sans accès aux données Firebase réelles. Les essais de règles utilisent uniquement l’émulateur local. Un constat décrit un comportement confirmé par lecture ou test ; « suspicion » signale une hypothèse non démontrée. Les numéros de ligne sont ceux des fichiers observés avant les corrections de cet audit ; rechercher l’identifiant pour retrouver une ligne après évolution.

## Modèle de menaces

| Acteur | Capacités et objectif | Protection attendue |
|---|---|---|
| Visiteur anonyme | Appeler directement Firestore/Auth sans interface | Refus par défaut et authentification requise |
| Utilisateur connecté malveillant | Modifier son client, forger des requêtes, pousser des données énormes ou consommer des quotas | Règles de propriété, validation serveur, limites et maîtrise des écritures |
| Attaquant sur appareil partagé | Ouvrir l’application après une session et lire les données locales conservées | Déconnexion qui attend les écritures et purge les données locales privées |
| Dépendance compromise | Exécuter du code au build ou dans le navigateur | Dépendances vérifiées, lockfile, CSP, CI à privilèges minimaux |
| Voleur de téléphone | Accéder à la session et au cache du navigateur | Verrouillage appareil, session révoquée, données locales minimisées |

### Points contrôlés sans constat exploitable

- Auth Google : popup sur ordinateur, redirect sur mobile/PWA ; COOP configuré `same-origin-allow-popups` pour préserver le popup. La connexion Google réelle ne peut être vérifiée sans compte OAuth de test et paramètres autorisés.
- Aucun lien utilisateur rendu en navigation HTML n’a été repéré dans les composants inspectés ; les liens sont exportés comme texte. Ne pas introduire d’URL cliquable sans validation `http:`/`https:` et `rel="noopener noreferrer"`.
- Manifest généré par Vite : nom, langue, mode standalone, racine `/`, icônes et raccourcis locaux ; aucune URL externe déclarée.
- Pas de source map publiée explicitement dans la configuration Vite. La production et les assets doivent être vérifiés dans `dist` après build.
- Les données personnelles observées sont adresse e-mail, nom/photo fournisseur si disponibles, préférences, tâches/listes/tags et dates. Elles résident dans Firebase Auth/Firestore et le cache local Firestore ; durée jusqu’à suppression par l’utilisateur ou purge des tâches de corbeille à 30 jours. Aucune suppression de compte réelle n’est implémentée : la route redirige vers les réglages.

## Recommandations de configuration manuelle

1. Firebase Console → Authentication : activer Email/Password et Google uniquement si utilisés ; activer la protection contre l’énumération des e-mails ; définir la politique de mot de passe après choix produit.
2. Google Cloud Console : restreindre la clé API Web aux référents HTTP exacts des deux origines et aux API nécessaires à Firebase Auth/Firestore ; ne pas considérer cette clé comme un secret.
3. Firebase Console → Firestore : publier les règles validées avec l’émulateur, jamais depuis cette session ; examiner les quotas et alertes Spark.
4. GitHub : activer l’alerte Dependabot, secret scanning et push protection ; configurer un workflow CI avec permissions minimales et actions SHA-pinnées.
5. Vercel et Cloudflare : conserver CSP/HSTS, domaines Preview dédiés au projet Firebase dev, domaines Production au projet prod, variables distinctes ; vérifier OAuth sur les deux origines.
6. Avant usage sur appareil partagé : mettre à jour DayFlow avec cette purge de cache ; conserver le verrouillage de l’appareil et éviter les profils navigateur partagés.
